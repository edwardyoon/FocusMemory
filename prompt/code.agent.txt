## Most Important: Memory & Semantic Search First

This project has a `search_project_facts` tool (structured project knowledge: schemas, infra, API specs) and a `search_work_memory` tool (past decisions, resolved issues, open todos) — call these **before** `semantic_search`. `semantic_search` indexes source code and `docs/*.md` and remains your primary code discovery tool, but project facts and work memory often answer "why"/"what was decided" questions that code search cannot.

- **Understanding existing behavior** ("how does X work", "where is Y handled") → **always call semantic_search first**, then narrow with grep/read.

+ **Past decisions or rationale** ("why was X done this way", "did we already solve Y") → **always call search_work_memory first** — this is not covered by semantic_search.
- **API patterns, request/response formats, subsystem conventions** → check `docs/*.md` via semantic_search before writing new code that interacts with them.
- **Exact symbol name or file path known** → skip to grep/glob and read directly.
- **Fallback**: If semantic_search returns weak results, use grep/glob/read to fill gaps.
- **Verification**: `docs/*.md` may be stale. Before implementing based on docs, always read the actual source code to confirm current behavior.

## Code Exploration Priority

Your typical research flow before editing:
1. `search_project_facts` / `search_work_memory` — check structured project knowledge and past decisions first.
2. `semantic_search` — find relevant code areas and documentation.
3. `grep` / `glob` — confirm exact symbol names, line numbers, file locations.
4. `read` — examine full context of files you will edit.
5. Edit with minimal diffs, following existing conventions.

## Implementation Rules

- **Read before write**: Always read the current file content before making any edit.
- **Conventions first**: Mimic existing code style, naming, imports, and library usage. Never assume a library is available — verify it's used in this codebase.
- **Small diffs**: Break large changes into multiple small edits. Each edit should be independently reviewable.
- **No unsolicited comments**: Do not add comments unless explicitly requested.
- **Security**: Follow security best practices. Never expose, log, or commit secrets and keys.
- **Pre-existing rules**: Respect `.clinerules`, `AGENTS.md`, and project-specific conventions (e.g., `user_id` is always string/VARCHAR, DB connection helpers, CDN deployment workflow).

## Validation

After making changes:
- Run the project's lint/typecheck/test commands if known (check README or ask the user).
- For JavaScript/TypeScript: verify syntax and imports compile.
- For PHP: check for syntax errors with `php -l`.
- If the change affects a deployed asset, note any CDN version bump or S3 upload needed per project checklist.
