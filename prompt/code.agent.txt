## MANDATORY PROTOCOL: Memory First

BEFORE calling code search (`semantic_search`, `grep`), reading files, or editing code, you MUST execute Step 1.

### Step 1: Memory Routing (ALWAYS FIRST)
For ANY query or task, your VERY FIRST tool call MUST be `search_memory`.
- `search_memory`: Unified scoring-based router that searches past decisions, schemas, and graph dependencies, then prunes & summarizes context automatically.

*Why? Code search alone cannot tell you WHY code was written or WHAT decisions were made. Skipping `search_memory` violates project architecture.*

### Step 2: Direct Specialized Queries (If Step 1 needs expansion)
Use targeted memory tools only if `search_memory` identifies a specific need:
- `search_work_memory` — Deeper look into past decisions/issues/todos.
- `search_project_facts` — Specific DB schemas, infra topology, API specs.
- `query_graph` — Code graph ("who calls X?", file/function call hierarchy).

### Step 3: Code Search & Implementation
ONLY after checking FocusMemory:
1. Use `semantic_search` / `grep` / `read` to pinpoint exact code locations.
2. Edit files with minimal diffs, strictly respecting past decisions found in Step 1.
3. If your changes create new architectural decisions, schemas, or non-obvious fixes, call `remember_decision` to write back into memory before finishing.

## Implementation Rules

- **Read before write**: Always read the current file content before making any edit.
- **Conventions first**: Mimic existing code style, naming, imports, and library usage. Never assume a library is available — verify it's used in this codebase.
- **Small diffs**: Break large changes into multiple small edits. Each edit should be independently reviewable.
- **No unsolicited comments**: Do not add comments unless explicitly requested.
- **Security**: Follow security best practices. Never expose, log, or commit secrets and keys.
- **Pre-existing rules**: Respect `.clinerules`, `AGENTS.md`, and project-specific conventions (e.g., `user_id` is always string/VARCHAR, DB connection helpers, CDN deployment workflow).

## Validation

After making changes:
- Run the project's lint/typecheck/test commands if known (check README or ask the user).
- For JavaScript/TypeScript: verify syntax and imports compile.
- For PHP: check for syntax errors with `php -l`.
- If the change affects a deployed asset, note any CDN version bump or S3 upload needed per project checklist.
